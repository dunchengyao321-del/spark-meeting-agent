# T11/T12 全链路对接与真实会议联调记录（2026-08-31）

## 结论：通过

会议室 ⇄ 飞书 ⇄ shim ⇄ bridge（8876）⇄ 星火管线（8765，火山 ASR 2.0 → 豆包 → 火山 TTS 2.0 → MCP）全链路闭环。

实测一轮真实交互：用户"我要去大坪时代天街" → ASR 准确识别 → 调用 Rokid navigate 工具 → 语音播报"好的，正在为你规划去大坪时代天街的路线，马上开始导航"。

延迟指标：首轮端到端 880ms（asr 584ms / retrieval 57ms / tts_ttfa 880ms）；含工具调用轮 3.4s。验收线 <2s 达标。

## 对接架构

`bridge_server.py --pipeline-url ws://127.0.0.1:8765/ws/meeting --downlink-gain 5.0 --pipeline-channel 0`

- 下行：shim 48kHz → pipeline_adapter（5x 增益 + ratecv 48k→16k + 声道字节）→ /ws/meeting
- 上行：/ws/meeting TTS 24kHz → ratecv 24k→48k → **20ms 实时整流器** → bridge → shim
- 打断：管线 clear_audio → 适配器清整流缓冲 → bridge.flush_uplink（清队列 + 通知 shim 清抖动缓冲）

## 联调中发现并修复的问题

| # | 问题 | 根因 | 修复 |
|---|---|---|---|
| 1 | 说话完全没反应 | 下行电平太低（RMS 0.01），管线噪声闸门丢弃 + ASR 幻听 | `--downlink-gain 5.0` |
| 2 | 喊"星火"没反应，识别成"金博" | 管线配置的唤醒名是"顿承尧/承尧/顿顿/deli/顿老师"，且免唤醒仅对主人声道生效 | 适配器加 `--pipeline-channel`：演示走 0（免唤醒直答），正式走 1（点名仲裁） |
| 3 | 智能体回答被"自己打断" | 手机扬声器外放回答 → 手机麦克风回收 → 管线判定 barge-in | 测试规约：戴耳机或回答时手机静音；真实会议中各端 AEC 自理 |
| 4 | 声音断断续续没有连贯性 | 管线 TTS 突发发送（100ms 音频 20ms 一发，5 倍速），撑爆桥接队列与页面抖动缓冲造成丢帧 | 适配器新增 **20ms 实时整流器**（_pace_loop），匀速喂帧 |
| 5 | 测试中途无语音输入 | 手机锁屏/App 退后台导致"假在线" | 测试规约：手机保持前台亮屏 |

## 复用与配置注意

- 复用的是星火服务器既有 `/ws/meeting`（[声道字节]+16kHz PCM 入，24kHz PCM 出 + JSON 事件）。
- 管线全局配置 `meeting_wake_required=false`、`meeting_wake_names=顿承尧…` 为当前演示生效值；若切回点名模式，把适配器声道改回 1 即可。
- 下行增益 5.0x 是针对"手机靠近说话"场景的调校值；会议室麦克风阵列场景可能需要调低。
