# 会议语音对话智能体 · 设计方案

> 版本：v0.1（设计评审稿） · 日期：2026-08-25
> 目标页面：`http://127.0.0.1:8765/`（现 `config_ui.py`，将重构为「会议控制台」）
> 定位：可开源复用的多人会议语音智能体。听得清、答得快、接得住知识库与 MCP。

---

## 1. 背景与现状

当前 8765 页面（`config_ui.py`）是一个内嵌 HTML 的本地配置页：

- 通过轮询 REST 接口，正则解析 `local_voice_agent.log` 还原对话，延迟高且脆弱；
- 语音链路是「单人 1:1」：麦克风 → OpenAI Realtime（`gpt-realtime`，服务端 VAD + 打断）→ 扬声器；
- 音频采集/播放绑定 `ffmpeg + avfoundation`（仅 Mac），页面与飞书工程、密钥配置混在一起；
- 没有知识库、没有 MCP、没有多人说话人区分、没有延迟指标。

与目标的差距：**不是优化一个配置页，而是把它升级为「会议语音智能体控制台」**，并把后端拆成可插拔、可开源的管线。

## 2. 设计目标（对应三条要求）

| # | 要求 | 设计承诺 |
|---|------|----------|
| 1 | 页面代码可复用、开源 | 前端拆为无构建静态站 `web/`，后端 FastAPI，配置全部走 `config.example.json` + 环境变量，MIT 协议，文档齐全 |
| 2 | 对话效率对标豆包/GPT，多人会议，听得清，含糊处按语义确认 | 全流式管线（流式 VAD/ASR/LLM/TTS）+ 打断；说话人分离与轮次仲裁；语义澄清器；语音到语音中位延迟 ≤1.2s |
| 3 | 接入公司知识库与 MCP，预判会议内容、快速回复 | RAG 摄入 + 混合检索；「预判式上下文预热」：别人说话时持续预测并预取上下文；MCP 工具调用 |

## 4. 前端会议控制台（要求 1：可复用、开源）

### 4.1 技术形态

- **零构建静态站**：`web/index.html + *.js(ES Modules) + *.css`，不依赖 Node/npm，clone 即用；
- 与后端仅通过 **一个 WebSocket + 少量 REST** 通信，协议在 `docs/protocol.md` 公开，方便第三方接自己的后端；
- 保留现有「设置页」能力（密钥不回显、只监听 127.0.0.1），但拆成独立路由 `/settings`。

### 4.2 页面结构

| 视图 | 内容 |
|------|------|
| 会议控制台（默认） | 参会人列表（谁在说话、累计时长）、逐句字幕流（说话人着色、流式灰色→定稿白色）、智能体状态灯（听/想/说）、打断按钮 |
| 延迟仪表 | 端点检测、ASR、检索、LLM 首 token、TTS 首包、端到端总时延（每次发言一条），开源用户可直接用来对比豆包/GPT |
| 知识库 | 文档列表、摄入状态、检索测试框（输入问题→看命中片段），MCP 服务器连接状态与工具清单 |
| 纪要 | 实时摘要、决议、行动项，会后导出 Markdown |
| 设置 | 现有配置项 + 各适配器（ASR/LLM/TTS/Embedding）选型与密钥 |

### 4.3 音频输入输出两种模式（开源可移植性关键）

- **浏览器模式（默认，跨平台）**：页面用 `getUserMedia` 采麦克风、`getDisplayMedia({audio:true})` 捕获会议标签页/系统声音；智能体语音通过页面播放。无需 BlackHole、无需 ffmpeg，任何电脑打开即用 —— 这是 GitHub 上别人复用的主路径。
- **会议桥接模式（Mac，接入真实飞书会议）**：沿用现有 `meeting_voice_host.py` + BlackHole 路由，把智能体语音注入飞书会议，把会议声音回灌给管线。作为 `integrations/feishu/` 可选能力保留。

### 4.4 前后端事件协议（节选）

```
浏览器 → 服务端:  audio.frames {channel:"mic"|"meeting", pcm16@16k}
                  session.start / session.stop / agent.mute / inject.say{text}
服务端 → 浏览器:  transcript.partial {speaker, text, conf}
                  transcript.final   {speaker, text, conf, ts}
                  agent.state        {listening|thinking|speaking|confirming}
                  agent.audio        {pcm/opus delta}   # 浏览器模式播放
                  metrics.turn       {endpoint_ms, asr_ms, retrieval_ms,
                                      llm_ttft_ms, tts_ttfa_ms, total_ms}
```

## 5. 低延迟语音管线（要求 2：对标豆包/GPT）

### 5.1 管线选择

现有 Realtime S2S（语音进语音出）延迟最低，但**无法干净地注入知识库检索结果与 MCP 工具调用**。因此默认采用可控的全流式文本管线，Realtime 模式保留为「闲聊低延迟档」开关：

```
音频帧 → Silero VAD(端点) → 流式 ASR(边说边转) → 轮次仲裁 → LLM(流式,带预热上下文)
     → 按句切分 → 流式 TTS(首句即播) → 浏览器/扬声器
```

### 5.2 延迟预算（语音结束 → 智能体首声）

| 环节 | 目标 | 手段 |
|------|------|------|
| VAD 端点判定 | 200–400ms | Silero VAD + 语义完整性判断（疑问句可更早收尾，`realtime_silence_ms` 思路沿用但动态化） |
| 流式 ASR 定稿 | ≤300ms | 流式供应商（火山流式 ASR / FunASR paraformer 流式），partial 已经在路上 |
| 检索 | ≈0ms | 预判式预热（见 §7.3），命中缓存直接用 |
| LLM 首 token | 300–600ms | 流式 + 精简 system prompt + 预热上下文 |
| TTS 首包 | ≤300ms | 流式 TTS，首个分句即合成 |
| **端到端** | **中位 ≤1.2s，P95 ≤2s** | 页面延迟仪表持续实证 |

### 5.3 打断（barge-in）

沿用现有 `input_audio_buffer.speech_started → response.cancel` 思路：任何通道检测到语音且智能体正在说话 → 立即停 TTS、丢弃待发音频、转入监听。页面同步状态灯。

### 5.4 「听得清」

- 16kHz 单声道上传前做浏览器侧降噪（`noiseSuppression`/`echoCancellation` 约束）；
- 会议模式建议佩戴耳机或启用回声消除，避免把智能体自己的声音再次识别（另可用「自己说话时暂停 ASR」的自屏蔽窗口兜底）；
- 转写置信度逐句记录，低于阈值进入 §6 澄清流程，而不是猜。

## 6. 多人会议模拟与轮次仲裁（要求 2）

### 6.1 说话人区分

- **声纹注册制（v1，最稳）**：复用现有 `voice_samples/` 录音流程，每位常驻参会人录 10–20s 生成声纹（ECAPA/CAM++ 嵌入）；会中每段语音先匹配已注册声纹，未匹配的归为「来宾 N」，页面上可随手改名；
- **自动分离（v2 增强）**：单声道会议混音上跑 pyannote/3D-Speaker 在线聚类，与声纹库对齐；
- 智能体永远知道「刚才是谁说的」，字幕与上下文都带说话人标签。

### 6.2 轮次仲裁：什么时候该智能体说话

模拟真人开会礼仪——**不抢话、被点名才说、说完就闭嘴**：

1. **显式点名**：说出唤醒名（默认「星火」，可配置）；
2. **明确移交**：如「星火你来说一下」「AI 帮忙查一下」；
3. **被直接提问 + 静默 2s**：上一句是对智能体的问句且无人接话；
4. **手动触发**：页面点「让星火说」；
5. 其余情况只转写、预热上下文、写纪要，不发声。
   多人同时说话（重叠）→ 继续监听并在纪要标注「讨论中」。

### 6.3 语义澄清（说得不清时按语义确认）

触发条件（任一）：
- ASR 置信度低于阈值；
- 关键实体在知识库/声纹库中有 ≥2 个近似候选（如「王总/黄总」、两个相似项目名）；
- 问句缺少必要槽位（时间/对象/金额等）且影响回答正确性。

确认话术规则：**一次只问一个二选一/补全式短问题**，例如「你说的是华东区还是华南区？」；用户确认后继续；若用户说「都不是」则请求重述。绝不把猜测当事实输出（与现有 system prompt 第 4、5 条一致）。

## 7. 知识库 + MCP + 预判（要求 3）

### 7.1 知识库摄入（等你把公司知识库发来后落地）

- 支持格式：Markdown / PDF / DOCX / TXT / 网页导出 / 飞书文档导出（按你提供的实际格式再补）；
- 流程：解析 → 语义切块（标题感知，300–800 字，重叠 10%）→ 向量化（本地 bge-m3 或供应商 embedding）→ 存入 **sqlite-vec**（零服务器、单文件，开源友好）+ BM25 关键词索引；
- 混合检索：向量 top-k ∪ BM25 top-k → 可选重排 → 引用片段带来源，智能体回答时**必须给出出处**，检索不到就明说。

### 7.2 MCP 接入

- 内置 MCP Host：支持 `stdio` 与 `HTTP/SSE` 两类服务器，`config.json` 里声明：

```json
"mcp_servers": [
  {"name": "公司内网工具", "transport": "stdio", "command": "npx", "args": ["..."]},
  {"name": "数据平台", "transport": "http", "url": "https://...", "headers": {"Authorization": "***"}}
]
```

- 启动时拉取工具清单并注入 LLM function calling；工具执行超过 600ms 时，智能体先口头垫一句「我查一下」，避免冷场；
- 只读工具可配置进「预执行白名单」（见 7.3），写操作一律在会话里口头确认后才执行。

### 7.3 预判式上下文预热（核心差异化）

别人说话时智能体不只是转写，而是**边听边猜接下来要答什么**：

1. 每收到一次 partial 转写（节流 ~1 次/秒），后台轻量任务：主题关键词 + 向量检索 → 候选片段写入 **上下文缓存**（TTL 60s）；
2. 每 30s 用小模型滚动更新「会议态势」：当前议题、各方立场、悬而未决的问题、可能问到智能体的点；
3. 轮到智能体发言时，直接取缓存组装 prompt（检索耗时≈0），未命中才现场检索；
4. 预执行白名单内的只读 MCP 工具（如查数、查排期）可提前执行并缓存结果，命中时秒回。

效果：把「检索 + 工具调用」的延迟从回答关键路径上挪走，是达到豆包级响应速度的关键一环。

- 适配器接口文档化：别人换 ASR/LLM/TTS/向量库只需实现一个接口并在配置里切换；

## 11. 风险与对策

- **单声道混音说话人分离难** → v1 以声纹注册为主、自动分离为辅；飞书侧若开放会中说话人信息可直接对齐；
- **浏览器捕获系统声音需用户授权且各平台差异大** → 页面内置引导与降级（仅麦克风模式），文档写清；
- **网络/代理波动（现有 `realtime_proxy` 场景）** → 沿用现有退避重连策略，所有外部适配器统一超时与重试；
- **知识库内容敏感** → 全本地存储与推理路径可选（本地 ASR/LLM/TTS 组合），开源文档给出「纯离线配方」；
- **合规** → 会议中启用智能体前提示参会者（延续现有 README 的披露原则）。

## 12. 待你确认的事项

1. 知识库载体形式（飞书文档导出 / 网盘文件 / Confluence 等）与大致规模；
2. MCP 服务器清单（stdio 还是 HTTP、是否只读）；
3. 是否接受默认选型（火山流式 ASR + 火山流式 TTS，需要相应密钥；也可全部换本地方案）；
4. 唤醒名默认「星火」是否合适；
5. 目标运行环境：仅本机 Mac，还是要兼顾同事的 Windows/Linux（影响 P4 桥接优先级）。
